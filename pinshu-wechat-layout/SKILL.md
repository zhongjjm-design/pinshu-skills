# 品叔公众号排版 v0.4.0-rc.2（试用版）

同一预览页提供七款版式（六款按颜色分，第七款“数字分栏”可带章题副题），可切换、可复制正文。只改版式，不改原稿文字，不自动写摘要或配图。

## 来源与维护

- 原创身份：品叔原创（original）
- 原创归属与维护者：Aidan（品叔）
- 上游依赖：Python 3.10 以上，`markdown-it-py`、`beautifulsoup4`；整篇入口可选搭配同仓库的 `pinshu-visual-system`。
- 分发状态：0.4.0-rc.2 公开试用版；不声明正式发布、tag、CI 通过或微信后台真机验收。

## 运行环境

需要 Python 3.10 以上。装依赖并自查：

```sh
python3 -m pip install -r requirements.txt
python3 scripts/doctor.py
```

最后一行是“全部就绪”才往下走。缺同级的 `pinshu-visual-system` 只影响整篇入口，单独 build.py 仍可用。

## 三步上手

1. 读用户明确指定的定稿正文和旁边的“发布物料包”，不要自己挑最新稿。
   **构建前重新绑定当前终稿。** 计算正文当前 SHA256，并核对 `配图清单.json.article_sha256`、每个图片/视频 `after_prefix` 和 `heading_split` 的键。写手在交接后更新终稿很常见：若只是 SHA 变化且全部锚点仍唯一存在，只更新交接清单哈希；若 H2 增加了编号或改名，同步把 `heading_split` 键改成当前完整 H2，拆分值拼回原章题；若任何锚点消失、不唯一或语义位置改变，停止构建并退回交接，不改正文迁就旧 JSON。
   **同时先核正文图比例。** 品叔公众号正文图默认按 16:9 横图验收；文件名叫“流程卡”“金句卡”也不能自动放行竖长卡。若交接出现 3:4、2:3、9:16 或需要连续滑动才能看完的正文图，而物料包和 Aidan 都没有明确指定长图，停止试排并退回视觉环节重排；不要用 CSS 压缩、裁切或窄屏缩放把平台错误藏起来。封面仍单独按 900×383 检查。
2. 整篇入口（推荐，交接文件自动生成）：
   `python3 ../pinshu-visual-system/scripts/run_ready_article.py --article <定稿正文.md> --kit <发布物料包.md> --output-dir <过程文件夹里的新目录> --space-id <ego空间号>`，没有浏览器把 `--space-id <ego空间号>` 换成 `--prepare-only`。
   只想排版：`python3 scripts/build.py --handoff 交接.json --output-dir 新目录`，交接文件照下面样例写。
3. 打开输出目录里的 `公众号图文排版预览.html`，切换七款，复制正文、标题、摘要。不要只看按钮存在：在真实浏览器里选定交付版式，实际点击一次“复制正文和配图”并确认成功提示，再点击“下载排版正文”保存独立带图 HTML；重新打开下载件，在 375px 下核图片全部内嵌并加载、图片与章节数量正确、文末参考区保留、无内部操作文案且无横向溢出。只有这组动作跑通，才可交付“可一键复制/可直接打开”的文件。

### 急发任务的快路径

用户明确说“马上发布”“尽快”时，不减少验收项，但把机械检查合并执行：用一段脚本一次核对正文 SHA、标题键、锚点、视频真源和图片哈希；只构建一个全新输出目录；浏览器里用一次批量脚本切换七款并检查 320/375/414px 的计数、图片加载和横向溢出。没有可替换媒体、且用户没要求微信真机验收时，不逐款人工截图、不开公众号后台、不追加解释；构建和批量验收通过后立即回传输出目录、预览页和关键结果。只要稿件含视频替换位或验收标准点名微信后台，就必须走后台真实替换路径；速度来自合并机械检查，不来自跳过平台清洗与替换验收。

最小交接文件样例（无配图）。`配图清单.json`：

```json
{"article": "正文.md", "article_sha256": "<正文文件的 SHA256>", "files": []}
```

`交接.json`：

```json
{"source_md": "正文.md", "image_manifest": "配图清单.json", "author": "作者名", "body_images": []}
```

SHA256 用 `shasum -a 256 正文.md` 算。有配图时，在 `files` 里列每张图的 `filename` 和 `sha256`，在 `body_images` 里写 `filename` 和放在哪一段后面（`after_prefix`，填那一段开头的几个字）。走整篇入口时这两个文件由视觉 Skill 自动生成，不用手写。

字段完整说明见 `references/handoff-and-rules.md`。

## 出错了怎么办

- 提示缺依赖：运行 `python3 -m pip install -r requirements.txt`，再跑 doctor。
- 提示 YAML 未闭合：正文开头的文件信息格式坏了。不手改原稿，退回写稿方用导出脚本重导。
- 提示代码块、原始 HTML 不支持：先告诉用户，不要悄悄删。表格和提示词卡片已支持（见 `references/handoff-and-rules.md`“表格与提示词卡片”）；表格超过 4 列会报错，退回写稿方拆表。
- 提示输出目录已存在：换一个新目录名，不要覆盖旧稿。构建在 SHA、锚点或 `heading_split` 校验阶段失败也可能已经创建目录；修正交接后用新的输出目录继续，不删除或复用失败目录冒充当前版。
- 提示 `Source Markdown differs from image handoff`：不要修改终稿。重新计算正文 SHA256，逐项确认图片/视频锚点仍唯一存在；只有锚点全通过时才把 `配图清单.json.article_sha256` 更新为当前值。
- 提示 `heading_split key is not an H2 heading`：重新读取当前正文的完整 H2；章节新增 `01` 等编号时，`heading_split` 的键和值也必须包含编号，并继续满足“大字 + 原分隔符 + 小字 = 完整章题”。
- 图有问题（模糊、字小、框重叠）：带原文位置退回视觉环节，排版这边不自己换图。
- 文末“参考文章”被排成了带编号的一章：属于错误。参考文章一律排成灰色斜体小字、靠左，不编章号（见 `references/handoff-and-rules.md`“参考文章”）。
- **视频位默认用读者安全卡片，不把操作说明放进正文。** 正文可写 `【此处在后台插入视频：视频名】`，排版只显示“▶ 视频名”的细边框卡片；交接也可用 `body_videos`，但两种写法不能同时存在。卡片必须由独立全宽普通段落和其后的独立清除段组成，禁止用 `section`、flex、grid 或 table 作为可替换容器——微信后台替换复杂容器时可能把真实视频与下一章并到同一横排。第七款章题也必须是单块标题：数字和竖线在同一个标题元素内定位，禁止做成可接收光标的左右格。`选中本行插入视频`、零行高、零字号、透明字和隐藏字等内部操作文案禁止进入最终富文本，因为微信清洗或深色模式可能令其暴露、重叠或形成异常空行。后台换成真实视频后，再确认真实视频独占一行、下一章另起一行，且卡片和标记都已消失（见 `references/handoff-and-rules.md`“视频位”）。

## 表格、提示词卡片、章题副题（2026-10-15 新增，待微信真机验收）

- Markdown 表格（2 到 4 列）直接排成窄屏表，超过 4 列报错。
- 正文里以 `> 【标题（小注）】` 开头的引用块排成提示词卡片，细线框，随版式配色。
- 第七款“数字分栏”的章题副题：交接文件写 `heading_split`，格式 `{"完整章题": ["大字", "小字"]}`，拼起来必须等于原章题。
- 规则、数值和已踩的坑见 `references/handoff-and-rules.md` 末尾几节。

## 交付与状态

- **七款只是候选，版式由 Aidan 选。** 未收到明确版式选择前，不推荐首选/备选，不把默认显示的青灰手记当成最终版，也不单独导出或交付某一固定模板的“最终粘贴 HTML”；先交七款切换预览。若用户明确要求“后台粘贴版”但仍未选版，七款各导出一份并按模板名标清，逐份核图片内嵌、章节、参考区、图片框和手机溢出，不替用户选一份冒充最终；用户选版后再把对应文件作为发布候选。
- **七款图片框的覆盖比例必须一致。** 头图和正文图统一使用 1px 细线、8px 圆角、4px 内边距，只允许边框颜色变化；构建后在同一宽度逐款测 `frame width / image width / left-right gap`，七款数值必须相同，不能仅凭肉眼看边框样式。

构建成功只说明本地试排通过，不等于可发布。交付前先做**发布对象完整性检查**：标题、作者、摘要、横封面、正文与正文配图必须逐项有真实值；只有用户明确要求省略的字段才允许为空。物料包已有标题／摘要候选时，执行方直接选择最贴合正文的一项填入，不留空等用户追问。验收必须读取字段实际值并真实点击“复制标题／作者／摘要／正文和配图”；按钮存在不算字段完成。随后核对：模板章号与正文标题没有重复数字；视频卡片数等于交接预期且 `data-video-slot`、`选中本行插入视频` 均为 0；提示词卡片和表格数量正确；正文链接数符合原稿；图片全部加载；320/375/414px 无横向溢出。任何修改后都从发布字段到独立下载件重跑整套，不只复查改动点。验收可编辑占位功能时必须执行用户会执行的动作：把富文本粘进微信公众号后台，删除整张视频卡片，插入真实视频，再检查下一章没有被吸进视频行。浏览器手机宽度截图只能写“本地移动端复核”；只有稿件经微信清洗、真实视频替换并发送到手机预览，浅色与深色都看过，才能写“微信真机验收”。用户选版、微信后台真机粘贴效果要分别如实记录，没确认前不写“可发布”。

## 紧急发稿与 Skill 开发边界

- 用户明确选定某款版式时必须忠实使用，不得因为实现困难擅自建议换版式规避问题。
- “今天必发”的生产任务默认冻结共享 Skill：只读取当前版本、构建和验收，不在正式稿上边排版边修改公共渲染器。
- 若用户明确把 Skill 修复交给 Claude 或其他 Agent，修复期间停止继续打补丁；对方完成后重新读取磁盘上的最新版，只负责用最新版重建与验收，除非用户再次明确授权修改 Skill。
- 自动测试、DOM 检查、375px 浏览器截图都不能替代微信公众号后台真实清洗。涉及视频替换、深色模式或复杂章题时，必须在后台粘贴、真实替换视频并完成手机浅色与深色预览后，才能报告通过。
- 不让用户充当排版引擎的回归测试员；未完成真机闭环时直接标注“未验证”，不要连续交付补丁版让用户试错。

# 交接字段与排版规则（细节）

从 SKILL.md 搬来的细节，内容未删减，只做了分段和去路径处理。

## 总原则

七款版式：松绿双线、青灰手记、暖纸杂志、橙线手记、蓝白专题、首席品牌官经典版、数字分栏（第七款，2026-10-15 加入）。七款都是正式版式，预览页默认显示青灰手记。可切换与复制只证明工具可用，不代表该版式已被用户选定。输入稿件、配图交接与逐篇编辑决定仍是每篇文章的权威源；不要从既有样稿替换文字，也不要自动编写摘要、重点句、事实或图片。

## 正常接活

先读取用户明确指定的待发布正文及旁边“日期_文章标题·发布物料包.md”，不自动挑最新稿。正文及物料包的开头 YAML、过程目录、任务路径和进度约定见已安装视觉 Skill 的待发布交接说明（pinshu-visual-system 里的 ready-folder-contract.md，经 router 定位后完整读取）。稿件的账号、定稿日期、写手模型、过程路径和配图排版进度属于文件信息，不排进正文。直接 build 也分离 YAML；未闭合则报错。正文和来源保留，原稿不改。

整篇入口：`<pinshu-visual-system>/scripts/run_ready_article.py --article <明确正文> --kit <配对物料包> --output-dir <过程目录内新试排目录>`，按环境传现有 `--space-id` 或 `--prepare-only`。它读取物料包任务路径并回写“配图排版进度”。单独运行 build 后也必须用该入口的 `--record-progress` 和 `--preview` 回写真实试排阶段及一键预览链接。用户选版和微信真机状态照实记录。

### 终稿在交接后更新：只重绑，不改正文

排版开始前重新计算 `source_md` 的 SHA256，并把当前正文与交接逐项比对：图片/视频 `after_prefix` 必须仍唯一命中；`heading_split` 的键必须是当前完整 H2。若写手只修改正文、锚点不变，更新 `配图清单.json.article_sha256` 后构建；若章节标题新增编号或改名，同步更新 `heading_split` 键和值，使两段与原标题分隔符仍能完整拼回当前 H2。任何锚点消失、不唯一或语义位置改变，都停止并退回交接，不修改终稿来适配旧 JSON。

构建校验失败后不要复用同名输出目录：失败可能已经创建目录。修正交接后换一个不存在的新目录，旧失败目录作为过程证据留存或按任务清理规则处理。

## 输入与运行

使用 `scripts/build.py`，需 Python 3.10+、`markdown-it-py` 和 `beautifulsoup4`。交接 JSON 至少包含 `source_md`、`image_manifest`，可填写 `author`、`digest`、`title`、`cover_landscape`、`cover_square` 与 `body_images`。路径相对于交接文件；封面与正文图片的文件名必须列于配图清单。配图清单包含 `article`、`article_sha256`、`files`（每项 `filename`、`sha256`）。正文配图项包含 `filename`、唯一的 `after_prefix` 与可选 `alt`。图片需是 PNG、JPEG 或 WebP。没有图片时，`files` 和 `body_images` 用空数组，不写封面字段。

```sh
python3 scripts/build.py --handoff /路径/文章交接.json --output-dir /路径/新试排目录
```

## 支持与不支持的结构

输入支持一个开头 H1、任意数量的 H2 章节、H3–H4、段落、引用、列表、分隔线和常见行内 Markdown。经典版图片章号素材覆盖 01–06；07 起使用文字章号，不改写或合并章节。遇到代码块、原始 HTML、内嵌图片等未覆盖结构，先说明限制，不能静默丢弃。每张正文图片以唯一原文段落开头定位；新增的图片不会改写正文文字。输出目录必须不存在，防止覆盖人工评审稿。

## 配图交接（2026-10-10 候选接口修订）

写稿交明确版本的正文与来源，视觉 Skill 负责 AI 生图、证据截图和实拍素材处理，排版只消费成图。唯一配图交接说明在已安装的 `pinshu-visual-system/references/article-asset-handoff.md`（通过 router 定位），不在排版复制一套来源/生成规则。排版发现图有问题，带上下文退回视觉环节，不自行生成替代图。

## frame_baked 与 caption

正文图片项可带 `frame_baked`、`caption`、`source_label`、`source_url`：已加框图传 `frame_baked: true`，逐图关闭模板衬框；新截图交无框原图、frame_baked 为 false；排版模板的衬框只作呈现，不烘焙进截图像素。旧已加框素材如实保留 frame_baked 记录，避免叠框。`caption` 是纯文字图注，不生成来源外链或重复署名。未填 caption 时优先文字来源署名，否则回退 alt；显式空 caption 不显示。`source_url` 保留机器记录，不需要手工删除；原稿资料来源及其链接不改。每段当前最多一图。带 `===EDITOR NOTES===` 的稿件由写稿工具导出正文及来源，不能混入编辑备注或在排版偷偷删掉。

## 整篇导出与手机检查

整篇导出、配图交接、轻量实际模板预览及手机检查，复用视觉 Skill 的 run_article_pipeline.py（详见唯一交接说明），不另拼 HTML。截图原像素够清晰仍可能在手机上字小；查看自动保存的逐图手机截图，有问题带原文位置退回视觉环节。工程检查、Agent 看图、用户验收与微信真机效果分别记录。

## 交付与状态（细节）

打开生成的 `公众号图文排版预览.html` 在同一篇文章上切换七款版式，检查整篇和配图；侧栏分别复制标题、作者、摘要，按钮单独复制当前版式的正文富文本和配图，或下载带行内样式的正文 HTML。`fields.json` 和 `试排记录.json` 保存字段、输入哈希与本地核验状态。空摘要保持空，不伪装成已审定发布文案。

每次按原稿段落、章题、图片数量与顺序核对输出，再检查 320/375/414px 宽度及原生粘贴结果。构建成功只代表本地试排；微信后台清洗、手机预览、稿件事实与图片审美仍需逐篇确认，未确认前不得写成「可发布」或「正式模板已验收」。七款试排是候选集，不代表 Agent 获得选版权：用户未明确选定版式时，不得擅自推荐首选或备选，不得把默认显示款当最终版，也不得单独导出某一款并命名为“最终粘贴 HTML”；只交七款预览，等用户选版后再导出对应固定 HTML。不自动登录、发布、归档或改写原稿。

## 出处

核对历史样稿、模板与章号素材出处时读取 `historical-template-provenance.md`；这些工程路径不作为运行依赖。


## 头图、图片边框、参考文章、划线句（2026-10-12 品叔定）

- **头图**：交接里有 `cover_landscape` 时，横版封面自动放在标题下、正文第一段前，带模板边框，随正文一起复制。个别文章不要头图时，交接写 `"lead_image": false`。
- **图片边框**：各款模板的头图和正文图都有边框，颜色随模板走，不出“光秃秃的图”。截图本身不加框（`frame_baked: false`）。
- **参考文章**：正文末尾以“参考文章”“参考资料”或“资料来源”单独成行开头的一段，按附录排：换一种字体（Georgia／宋体）、灰色、小一号、斜体，跟正文明显区隔。
- **划线句**：交接里的 `emphasis` 列出作者选定的正文原句，最多 3 句，每句必须在正文里只出现一次；排版给这几句加一条细（1px）、亮色（琥珀黄或橙黄）的下划线，文字本身不加粗。没有作者选定就不划线，Agent 不自动挑。

## 视频位

视频位有两种输入方式，只选一种：

1. 作者在正文独占一行写 `【此处在后台插入视频：视频名】`；
2. 交接文件写 `body_videos`，每项含唯一段落锚点 `after_prefix` 和读者可见名称 `label`：

```json
"body_videos": [{"after_prefix": "Min Choi 那条", "label": "Min Choi 原片"}]
```

排版输出统一为读者安全卡片：一圈细边框、一个播放符号和视频名，例如“▶ Min Choi 原片”。正文中不得出现“选中本行插入视频”“此处插入视频”等内部操作说明；零字号、零行高、透明字或隐藏字也不得用来承载操作提示。微信会在深色模式和清洗后重新解释这些样式，未替换的提示可能暴露、重叠或形成异常空行。

若正文标记和 `body_videos` 同时存在，构建直接报错，先选定唯一真源；不要靠渲染阶段猜哪一个有效。同一段后面只能放一张图或一个视频，不能把图片节点临时替换成视频，否则会遗留图片外框和间距。

后台插入真实视频时，由操作者按交接说明定位并替换整张视频卡片；内部操作步骤放在文章外的交接记录中。视频卡片必须输出为独立全宽普通段落，并在后面保留一个独立的 `clear:both` 分隔段；禁止把可替换卡片做成 `section`、flex、grid 或 table，微信编辑器替换复杂容器时可能把真实视频与下一章吸进同一横排，造成视频占左栏、章题占右栏、章号掉到视频下方。若下一章使用左右视觉结构，章题也必须保持为单块标题，不能存在独立可编辑的左格。

视频验收按真实操作顺序执行：复制当前版式富文本 → 粘进微信公众号后台 → 删除整张读者卡片 → 在原位置插入真实视频 → 检查真实视频独占一行且下一章完整另起一行 → 发送手机预览 → 浅色、深色各检查一次。替换后卡片、正文标记、`data-video-slot` 和内部操作文案都必须为 0。若当次不插视频，保留干净的读者卡片或明确生成无视频版，不能留下内部提示。

本地 320/375/414px 截图只算移动端模拟，静态卡片正常也不能证明替换路径正常；必须完成微信公众号后台清洗、真实视频替换和手机浅色/深色预览，才算微信真机验收。

## 参考文章（2026-10-12 品叔定）

文末“参考文章”（也认“资料来源”“参考资料”）一律排成参考区：标题和条目都是灰色、斜体、比正文小（12.5px），靠左排，不两端对齐。它不是一章：不编章号、不画章题线、不算进章节数。正文结束和参考文章之间放一条居中的短线（约 40px、1px、用当前版式主色），上方留 48px、下方 28px；不用通栏线，也不用小圆点（品叔 10-12 看过三种样张后定）。写稿 1.3 交的是二级标题 `## 参考文章`，旧稿可能是普通段落，两种写法排出来一样。

**结尾总结图与参考区二选一收口。** 没有参考区的文章，可以把总结图／金句图放在最后一个正文段落之后，作为全文最后一个视觉节点。有参考区时，短分隔线应直接承接正文文字，禁止把总结图夹在正文结尾与分隔线之间；视觉环节默认省略该图，或把它提前到结论段之前的自然锚点。排版发现“正文 → 图 → 短线 → 参考区”时，停止构建并退回视觉交接，不靠压缩间距掩盖。

## 图片框和深色模式（2026-10-12 品叔定）

七款的图片框只用细线、8px 圆角和留白，不加底色（2026-10-15 起七款统一圆角；此前只有松绿双线、青灰手记是圆角）。七款图片框的内边距统一为 4px：同一张图在七款里的内容宽度和覆盖比例必须一致，只允许边框颜色随模板变化；不得让松绿或青灰因更大的内边距而显得图片被额外压缩。原因：微信手机端开深色模式时，会把图片框的浅色底色改成浅灰，在黑色页面上显成一条宽边；浅色模式下看不出这个问题。10-12 用后台预览链接在电脑上模拟深色模式实测确认：去掉底色后，深浅两种模式都只剩一圈细线。

以后改版式，凡是浅色底色的元素（图片框、章题底衬等），都要在深色模式下也看一遍：把后台预览链接发到手机，深色、浅色各看一次。

## 表格与提示词卡片（2026-10-15 开发中，微信真机验收前不进正本）

### 表格

Markdown 表格排成固定布局的窄屏表：`table-layout:fixed`，列宽比例锁死，13px 无衬线字，细框，表头只用颜色和下边线区分（不加粗、不加底色，避免深色模式把浅底改成灰带）。3 列时比例 22%／38%／40%，2 列 30%／70%，4 列 16%／28%／28%／28%。超过 4 列报错，退回写稿方拆表，不硬挤。第一列是“起止时间”（如 `00.000 - 02.400`）时，在“ -”之后换行，保证数字不被拆开；单元格末尾的全角括号（如音效标记）改成灰色。文字一字不改，只做版式。

### 提示词卡片

正文里以 `> 【标题（小注）】` 开头的引用块，排成独立卡片：标题栏显示标题，小注用作者自己写的括号内容，不另加提示语；正文逐行排，行首“xx：”的标签（6 字以内）用琥珀色。引用块里列表下面紧挨着的行，按提示词里的独立行处理（Markdown 里它们属于上一条列表项的延续）。

定位：卡片是文章的一部分，不是重点强调的内容，地位和配图相当，不抢小标题、不抢金句（品叔 10-15 两次纠正：先嫌黑块突兀，再嫌绿底、粗竖线、深色标题带“太浓太死板”）。所以做成和当前版式「图片框」同一家人：只用一圈细线，线色取该版式图片框的值，圆角七款统一 8px（品叔 2026-10-15 定：图片框和卡片同一个角度，原先暖纸、橙线、蓝白、经典和第七款的直角一并改圆），不加底色、不加竖线、不加深色标题带。标题只是一行 12.5px 小字加一条同色发丝线；正文 14px，比正文略小，用正文同色；行首标签用该版式的主色。具体色值见 `assets/renderer.js` 的 `CARD`。不用渐变、阴影、胶囊、斜体、加粗。不加底色的原因：微信深色模式会把浅色底改成灰带（10-12 图片框的先例），去掉底色后深浅两种模式都只剩一圈线。排版新元素时，要拿带配图的稿子排在一起看，不能只看没配图的稿。正文是纯文字段落（不用代码块标签），微信里长按能选中；微信不支持脚本，做不了一键复制按钮。

### 验收状态

电脑浏览器实测：六款在 375、414 宽度下表格不溢出；320 宽度下时间列比内容窄 5px，无横向溢出。微信后台真机粘贴、深色模式：待品叔实测。

### 蓝白专题章标题（2026-10-15 品叔定）

原先是整块浅蓝底色加左侧粗线，数字装在色块里，显得笨重，浅蓝底在微信深色模式下也有变灰带的风险。改成不带底色：章号用浅蓝色，下面一条 1px 蓝细线通栏，再是章题，和其他线条分隔的版式同一思路。只改蓝白专题，其余五款不动。

### 第七款“数字分栏”与章题副题（2026-10-15 样张，待品叔定）

参考一篇外部文章的小标题做成：左边大数字（42px，字重 300，中性灰 #8a8f98），中间一条 1px 浅灰竖线，右边是大字章题（20px）加一行小字副题（13px，灰）。章题必须是一个不可拆的单块 H2：数字与标题用同一 H2 内的两个 `inline-block` span 呈现，竖线是数字 span 的右边框；禁止使用 flex、grid、table 或 absolute 定位。数字区占 25%，必须同时使用 `white-space:nowrap`、`word-break:keep-all` 和 `overflow-wrap:normal`，防止微信清洗后把“01”拆成上下两行。原因有三：微信后台替换前一个视频卡片时可能把视频吸进 flex/table 的左格；微信手机深色预览会清洗 absolute 定位，导致数字掉到标题上方；数字若继承正文断词规则，会被拆成单个字符。单块 H2 加不可换行的普通行内块同时避开这三类问题。

副题不能由 Skill 编：交接文件里用 `heading_split` 指定哪一章怎么拆，格式 `{"完整章题": ["大字", "小字"]}`；大字、一个分隔符（，：｜； 或对应的半角符号，或没有分隔符）、小字拼起来必须正好等于原章题，对不上就报错。没指定的章不拆，只显示大字，高度略高一点点。只有“数字分栏”这一款读 `heading_split`，其余款不受影响。

颜色用中性灰（品叔 10-15 嫌参考文章的亮蓝难看）：数字 #8a8f98，竖线 #dfe1e4，图片框、卡片、表格也用同色系的浅灰，不带色相。

### 暖纸杂志、橙线手记章标题（2026-10-15 品叔定）

原先是“顶上一道线 + 数字 + 章题”：线不隔开任何东西，悬在数字上面；橙线手记那条还是 2px 的饱和橙，最扎眼。改成松绿双线的结构：数字在上，章题上下各一道 1px 浅线夹住（暖纸 #d9c9b4，橙线 #eccdb9），线比字浅，退在后面；数字 28px、字重 400。青灰手记保持原样。

### 表格与提示词卡片的拒收规则（2026-10-15 独立复核后加）

为了不静默丢内容，构建时直接报错的情形：表格某一行的单元格数和表头不一致；表格或提示词卡片里有链接（会丢地址，改成纯文字或把链接放正文）；提示词卡片里有嵌套引用、代码块、嵌套列表，或段落、列表以外的块；`heading_split` 不是对象、键不是文章里的二级标题、值不是两段非空文字；章题拼不回原标题。交接文件里出现不认识的字段只警告不拒绝（防止把 `heading_split` 拼错了却没发现）。

### 第七款栏宽（2026-10-15 品叔定，Claude 改）

数字栏 22%、章题栏 78%，数字右边留白 12px、章题左边留白 16px。原先 25%/75% 时数字右边到竖线之间约 31 到 35 像素空白，而竖线到章题只有 16 像素，左右不对称。22% 是下限：320 宽屏手机正文约 288 像素，22% 为 63 像素，装得下两位数 "01"（约 46px 字宽加 12px 留白和 1px 竖线）；再窄会压到竖线。

# Value-First Course Delivery, Dissemination Assets, and Write-State Discipline

## When to Use

Use this reference when the user continuously submits transcripts from courses, talks, or live presentations and wants course assets that can be learned, executed, disseminated, and preserved over time.

## 1. Start by Answering Why the Material Is Being Organized

The primary task is not to demonstrate editorial rigor or put risks and pending verification in the most prominent place. It is to extract the assets the user should actually retain:

1. The course’s most important judgments;
2. Complete methods, reasoning, and cases;
3. Executable actions, tools, and critical numbers;
4. Distinctive direct wording from the instructor;
5. Material that can become the user’s content, decisions, and business actions.

Fact verification and applicable boundaries matter, but belong in an appendix by default. Only when a risk directly changes execution safety or the truth of a conclusion should a concise notice appear beside the relevant body passage; still consolidate the full explanation at the end.

## 2. Default Reading Order for One Lesson

```text
Lesson core (no more than 3 points)
→ faithfully edited transcript
→ systemized methods and complete cases
→ execution checklist, tools, and critical numbers
→ dissemination asset cards
→ social-post topics or candidate copy
→ editorial verification and boundary notes (appendix)
```

### Standard for the Opening Core

The opening exists only to help the reader grasp the main line quickly:

- Use no more than three main conclusions by default; add at most one line for a secondary judgment when necessary;
- Each point contains only “stage/problem + core action,” not cases and explanations repeated later in the body;
- Keep at most one source-information line after H1. Put document type, image state, STT corrections, and editing process in frontmatter or at the end;
- Do not let verification notes, disclaimers, or fragmented details dominate the opening visually.

**Completeness does not require a long opening.** The faithful transcript must still preserve the entire argument, cases, numbers, and limitations. Compress redundant navigation and editorial metadata, not course content.

## 3. Dissemination Asset Cards Are Required

Every lesson must contain at least:

### 1. Three to Eight Direct Quotations

They must come from the instructor’s actual words. Correct only punctuation, slips of the tongue, and confirmed STT errors. Never present editorial extraction as a quotation.

### 2. One to Three Disseminable Viewpoints

For each, specify the viewpoint, course basis, application, and boundary against blind copying.

### 3. One to Three User Connection Points

Connect proactively to the user’s current business, content themes, projects, and real experience. If no real context exists, write “real scenario required” rather than inventing first-person experience.

### 4. Zero or One Candidate Social Post

Generate one only when a real scenario, single tension, standalone narrative, and user style align. If the material is not mature enough, still provide a topic, applicable scenario, and missing information rather than omitting the entire dissemination layer.

## 4. Failure Signals for Distorted Priority

Rework if any of the following occurs:

- The closing verification note is more prominent than the course-value section;
- Large sections explain wording or minor risks that do not affect core understanding;
- A complete transcript exists, but there are no three-or-fewer scannable lesson-core points;
- The opening core exceeds three points, or each point expands cases already covered in the body and creates duplicate reading;
- Methods and cases exist, but direct quotations, disseminable viewpoints, or user connection points are missing;
- Social copy becomes “Today I listened to Teacher X’s course”;
- The file is long, but the reader still cannot tell what the lesson is useful for.

Rework in this order: reduce the opening to three core points, complete dissemination assets, reposition risk notes, then verify body completeness. Never create brevity by deleting cases.

## 5. Separate Content Completion from Durable Write Completion

Use only these states:

1. `Content organized; not yet written`;
2. `Files written; readback acceptance pending`;
3. `Written and accepted`.

After the user approves writing, the next action must be an actual file write—not more explanation, another request for synonymous confirmation, or a move to the next lesson. Report “saved to the library” only after the file exists and the title, frontmatter, key sections, case count, and closing conclusion have been read back.

If the user says “I cannot see the file” or “it is not on disk,” resolve file state before discussing layout improvement or the next lesson. Never substitute “content has been organized” for durable delivery.

## 6. Acceptance Checklist

- [ ] The opening contains no more than three core conclusions, with no meta explanation or duplicated expansion;
- [ ] There is at most one source-information line after H1; image/STT/editing notes are in frontmatter or at the end;
- [ ] The faithful transcript preserves first person, process, numbers, and cases;
- [ ] The structured lecture can be learned independently of the original video;
- [ ] Execution actions, tools, and numbers are complete;
- [ ] Direct quotations, disseminable viewpoints, and user connection points are present;
- [ ] The social layer does not invent user experience;
- [ ] Verification and boundary notes appear at the end unless a risk requires a local warning;
- [ ] Approved writes execute immediately without repeated gating;
- [ ] “Written” is supported by actual file-readback evidence.

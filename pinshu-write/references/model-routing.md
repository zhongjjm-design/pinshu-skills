# 模型路由

模型菜单会随工具、版本和账号改变；每次以当前工具实际提供为准。本文件保存分工原则，不把某个私人账号的模型列表当公开硬规则。

## 谁做什么

| 角色 | 选择原则 | 备注 |
|---|---|---|
| 写作者 | 当前可用的强中文长文模型 | 一篇文章只用一个主写作者 |
| 第二写作者 | 另一供应商的写作级模型 | 可用于竞争大纲或第二开头，由作者选 |
| 结构审稿 | 不同于写作者供应商的两个模型 | 用是/否问题，可答无法判断 |
| 反方与常识底线 | 两三个不同供应商模型 | 盲区不同才有价值 |
| 外行读者 | 另一供应商模型或真实同事 | 检查卡点与可扫读 |
| 事实核查 | 能联网或能读来源的模型 | 高风险项仍由作者抽查 |
| 机械任务 | 任意模型 | 文件处理、跑脚本、格式化、收链接 |

不要把“同一个供应商多个会话一致”当交叉验证。只有一个模型时，优先把审稿提示词交给另一个工具或真实读者；实在没有，就在编辑说明记录“同供应商审稿”。

## 搭配规则

写作者和审稿者尽量不同供应商。国内模型环境也可互相错开：一个负责起草，另一个做结构审查，第三个做反方或外行扫描。审稿者只标问题，不重写全文。

## 工具备注

工具显示的模型名可能变化；看到同系列新版本时，优先试新版本，并用 `references/review-chain.md` 的埋错测试重新校准。不要因为某工具默认模型方便，就用它承担所有角色。

## 只有一个模型时

常识底线、反方、结构审稿和外行读者都要尽量换上下文、换提示词、换材料视角。编辑说明必须写明限制，不把单模型复核说成多方审稿。

## 需要盯住的习惯

有的模型爱写口号，有的爱过度顺从作者，有的事实自信过高，有的中文句子发硬。审稿链要利用差异，而不是让模型互相吹捧。

## 输入要小

每个角色只给它完成任务所需的材料。结构审稿不需要所有来源；事实核查需要来源和 claim；标题冷读只给读者画像和标题。
